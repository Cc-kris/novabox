## 0. 一页结论

Novabox 是一个驻留在 Codex、Claude Code 等 Agent 桌面窗口旁边的**通用可复用工具箱**。它由独立桌面侧窗、窗口追随模块、本地工具内核和 MCP 适配层组成。

它解决两类问题：

1. 用户在 Agent 会话中解决过一次的问题，下次仍需重复解释、重复找规则、重复执行。
2. 对话适合探索，却不适合高频、固定、结构化的重复操作。

Novabox 的核心闭环：

> 会话中形成方法 → 受约束地生成工具草稿 → 自动校验与测试 → 用户确认发布 → 右侧手动使用 → 新会话由 Agent 搜索并调用 → 右侧自动展开、填参并展示结果。

V1.0 的产品边界是：**通用工具平台，不是某一个行业的计算器集合；不是任意代码生成器；不是 Codex/CC 的替代品。**

关键可行性判断：

- 正常窗口移动、缩放、最小化、恢复、多显示器切换，可以通过操作系统窗口事件可靠追随。
- 宿主真正最大化时，同一块屏幕没有额外外贴空间，必须提供“工作区布局、覆盖、自动收起”三种策略。
- Codex/CC 通过 MCP 使用同一个本地工具内核；Novabox 不依赖修改宿主内部 UI。
- 工具页面由 Schema 和白名单组件渲染，首版禁止直接执行 Agent 生成的任意脚本。

## 1. 产品定义

### 1.1 产品名称

**Novabox**

- `Nova`：新的方法、新的工具从一次探索中诞生。
- `Box`：可保存、可组织、可重复打开的工具容器。
- 品牌不强调“AI 魔法”，强调**沉淀、可靠、可复用**。

### 1.2 产品定位

> Codex / Claude Code 的可复用工具层。

品牌主张：

> **让方法，成为工具。**

辅助表达：

> 聊出来的经验，留下来成为工具。  
> Turn know-how into tools.

### 1.3 目标用户

- 已习惯使用 Codex、Claude Code 的开发者、独立创作者和小团队。
- 经常把业务流程、规则和数据交给 Agent 处理，但重复操作成本高的人。
- 需要把个人经验沉淀成固定工具，又不愿每次单独开发完整应用的人。
- 后续可扩展到运营、电商、财务、数据分析、研究等专业知识工作者。

### 1.4 产品价值

| 价值 | 说明 |
|---|---|
| 复用 | 一次生成，持续手动或由 Agent 调用 |
| 稳定 | 固定输入、处理逻辑和输出，减少每次问答差异 |
| 高效 | 无需离开熟悉的 Codex/CC 工作环境 |
| 可视 | 结构化表单、结果、来源和状态比长对话更易使用 |
| 可管理 | 工具有版本、测试、权限、来源和运行记录 |
| 可迁移 | 工具包独立于单个会话和单个宿主 |

## 2. 核心用户场景

### 场景 A：从当前会话沉淀工具

1. 用户与 Agent 完成一次可重复的问题处理。
2. 用户输入：`@Novabox 把刚才的方法保存成工具`。
3. Agent 先搜索现有工具，决定复用、升级或新建。
4. Agent 生成草稿，提交输入、输出、处理步骤、来源和测试。
5. Novabox 校验并运行测试。
6. 右侧打开预览，用户检查后发布。

### 场景 B：不打开 Agent，直接手动使用

1. 用户从右侧工具库打开工具。
2. 填写或粘贴输入。
3. 点击运行。
4. 查看结果、依据、异常提示，并复制或导出结果。

### 场景 C：新会话直接贴数据调用

1. 用户输入：`@Novabox 处理一下这批数据：……`。
2. Agent 调用 `novabox.search_tools`。
3. 读取候选工具说明和输入 Schema。
4. 将自然语言映射成结构化参数。
5. 调用 `novabox.run_tool`。
6. Novabox 执行同一工具内核。
7. Agent 返回结果，右侧同步打开工具、填入参数并展示本次运行。

### 场景 D：没有合适工具

1. 搜索返回无高置信候选。
2. Agent 不强行调用相似工具，不伪造结果。
3. 用户可以继续普通问答，或明确要求生成新工具草稿。

### 场景 E：宿主窗口变化

- 拖动宿主：Novabox 同步跟随。
- 缩放宿主：Novabox 同步位置和高度。
- 最小化宿主：Novabox 同步隐藏。
- 恢复宿主：重新获取窗口边界并恢复。
- 切换显示器：按新屏幕 DPI 和工作区重新布局。
- 宿主关闭：按设置隐藏，或切换成独立工具箱。

- 运行历史及敏感数据不保存选项。
- 工具更新差异与回滚。
- 窗口追随诊断和 MCP 连接诊断。

- 不默认上传用户工具、会话或业务数据到云端。
- 不承诺真正的宿主原生全屏模式下仍能外贴显示。

## 4. 窗口追随与桌面行为

### 4.1 技术原理

Novabox 使用操作系统公开窗口能力监听宿主，不依赖宿主提供侧栏插件接口。

**Windows：**

- 使用 `SetWinEventHook` 等机制。
- 监听位置尺寸、最小化、恢复、前台、销毁事件。
- 处理多显示器和 Per-Monitor DPI。

**macOS：**

- 使用 Accessibility API / `AXObserver`。
- 监听窗口位置、尺寸和状态。
- 引导用户授予辅助功能权限。
- 事件不足时使用轮询校正。

策略：**系统事件驱动为主，轮询校正为辅**。拖动期间提高更新频率，静止后降低资源消耗。

### 4.2 外贴坐标

默认外贴在宿主右侧：

```text
novabox.x      = host.x + host.width
novabox.y      = host.y
novabox.height = host.height
novabox.width  = 用户设置宽度
```

默认可选宽度：320、360、400、440、480 px；用户可拖动分隔边缘调整。窗口管理使用逻辑坐标与物理像素转换，避免高分屏漂移。

### 4.3 最大化策略

宿主真正最大化时，同屏外贴没有物理空间，提供三种设置：

| 模式 | 行为 | 适用 |
|---|---|---|
| 工作区布局（默认） | 宿主占据屏幕工作区减去侧栏后的区域，Novabox 占剩余区域 | 不想遮挡内容 |
| 覆盖 | 宿主保持最大化，Novabox 覆盖右侧 | 临时高频操作 |
| 自动收起 | 缩成边缘入口，点击后覆盖展开 | 需要最大化宿主内容 |

### 4.4 状态表

| 宿主状态 | Novabox 行为 |
|---|---|
| 移动/缩放 | 同步更新位置与高度 |
| 最大化 | 执行用户选择的最大化策略 |
| 最小化 | 同步隐藏 |
| 恢复 | 重新绑定并恢复 |
| 前台激活 | 恢复正确层级，不遮挡其他应用 |
| 失去前台 | 隐藏或降低层级，不全局悬浮 |
| 关闭 | 隐藏或进入独立模式 |
| 多窗口 | 跟随活动窗口，可手动锁定某个窗口 |
| 多显示器 | 重新计算工作区、缩放与可用空间 |
| 原生全屏 | V1.0 收起或转独立模式 |
| 权限失效/事件丢失 | 轮询校正；仍失败则提示重新授权 |

### 4.5 宿主识别

- 优先使用应用标识、进程与窗口对象标识。
- 窗口标题只作为辅助，不作为唯一依据。
- 记录用户最后绑定的宿主。
- 多宿主同时运行时由用户选择默认优先级。
- 防止 Novabox 自己被识别为宿主。

## 5. 产品功能与信息架构

### 5.1 一级导航

1. **工具**：搜索、最近、收藏和全部工具。
2. **运行**：当前工具页面和本次结果。
3. **草稿**：待验证、待确认、验证失败的工具。
4. **历史**：按工具、时间、来源筛选的运行记录。
5. **设置**：宿主、窗口、Agent、权限、外观、数据。

窄窗口下采用顶部图标导航或底部紧凑导航，不堆叠多层侧栏。

### 5.2 工具库

- 搜索框与命令入口。
- 最近使用、收藏、全部工具。
- 分类、标签和权限标记。
- 工具名称、用途摘要、版本、来源更新日期。
- 草稿、已发布、已停用状态。
- 空库时提供“从当前会话创建”和“导入工具包”入口。

### 5.3 通用工具页面

输入组件白名单：

- 文本、长文本、数字、日期。
- 单选、多选、下拉、开关。
- 单位选择、键值对。
- 可重复条目、表格输入。
- 文件输入作为后续扩展。

输出组件白名单：

- 结果摘要、指标列表。
- 表格、分组明细。
- 处理步骤和警告。
- 来源引用。
- 文本/JSON 复制。
- 下载结果作为后续扩展。

通用操作：

- 运行、重置、复制结果。
- 保存输入预设。
- 查看依据和版本。
- 创建副本、编辑草稿、停用。
- 报告异常结果。

### 5.4 草稿与发布

- 草稿差异视图。
- Schema 校验结果。
- 权限申请说明。
- 测试结果与失败原因。
- 工具预览。
- 用户确认发布。
- 已发布版本不可原地覆盖，只能创建新版本。

### 5.5 设置与诊断

- 宿主识别与窗口绑定。
- 外贴/覆盖/独立模式。
- 侧栏宽度、最大化行为、最小化联动。
- 全局快捷键、开机启动。
- Codex/CC 接入状态。
- 是否允许自动打开页面。
- 自动执行白名单。
- 深色、浅色、跟随系统。
- 数据保存、导出、清理和备份。
- 一键诊断：窗口权限、核心服务、MCP、数据库、工具索引。

## 6. 总体技术架构

```text
┌────────────────────────────────────────────────┐
│ Novabox Desktop：Tauri + React + TypeScript    │
│ 工具库 / 工具页 / 草稿 / 历史 / 设置            │
└──────────────────────┬─────────────────────────┘
                       │ 本地 IPC + 事件
┌──────────────────────┴─────────────────────────┐
│ novabox-core：唯一本地工具核心                  │
│ 注册库 / 搜索 / 校验 / 执行 / 版本 / 权限 / 日志 │
└───────────────┬────────────────────┬───────────┘
                │                    │
     ┌──────────┴─────────┐  ┌───────┴───────────┐
     │ MCP / Host Adapter │  │ Native Window     │
     │ Codex / Claude Code│  │ Tracker           │
     └────────────────────┘  └───────────────────┘
                │
                ▼
       同一个工具包与执行内核
```

### 6.1 推荐技术栈

- 桌面壳：Tauri。
- UI：React + TypeScript。
- 原生窗口追随：Rust + macOS/Windows 原生 API。
- 核心服务：本地常驻 `novabox-core`。
- 数据：SQLite + 文件系统工具包。
- UI 与 MCP：通过本地 IPC 访问同一核心。
- 本地事件：`tool.open`、`tool.input`、`tool.completed`、`tool.failed`。

MCP 启动时若核心未运行，可以自动启动；桌面端随后连接同一实例，避免多份工具库和状态分裂。

### 6.2 核心原则

```text
手动点击工具 ─┐
              ├─→ 同一个 Tool Executor → 同一份结果
Agent MCP 调用 ┘
```

禁止桌面 UI 与 MCP 各自复制一套业务逻辑。

## 7. 通用工具模型

### 7.1 工具能力分类

| 类型 | 能力 |
|---|---|
| 表单工具 | 收集结构化输入并输出结果 |
| 规则工具 | 条件判断、规则匹配、数据校验 |
| 计算工具 | 表达式、公式、单位换算 |
| 转换工具 | 字段映射、格式转换、数据清洗 |
| 流程工具 | 多步骤输入、检查、处理、输出 |
| 模板工具 | 固定模板生成文本或结构化内容 |
| API 工具 | 调用经授权、声明 Host 的接口 |
| Agent 协作工具 | 必要时让 Agent 补充非结构化理解 |

V1.0 优先实现：表单、表达式、条件规则、数据转换、多步骤、结构化输出。API 与文件能力默认关闭，单独授权。

### 7.2 工具包结构

```text
tools/
  <tool-id>/
    <version>/
      tool.yaml
      tests.json
      README.md
      assets/
```

### 7.3 工具定义示例骨架

```yaml
apiVersion: novabox/v1
metadata:
  id: unique-tool-id
  name: 工具名称
  version: 1.0.0
  summary: 解决什么问题
  scenarios: []
  keywords: []
inputs:
  schema:
    type: object
    properties: {}
    required: []
view:
  layout: sections
  sections: []
execution:
  type: workflow
  steps: []
outputs:
  schema:
    type: object
sources: []
permissions:
  network: false
  filesystem: false
  sideEffects: false
tests:
  file: tests.json
```

### 7.4 受约束执行 DSL

V1.0 支持：

- `set`：设置变量。
- `calculate`：运行受支持表达式。
- `validate`：按规则校验。
- `switch`：条件分支。
- `transform`：白名单数据转换。
- `template`：固定模板输出。
- `map`：对结构化列表逐项应用受支持步骤。

不支持：

- `eval` 和动态模块加载。
- 任意系统命令。
- 未声明的网络访问。
- 任意读写文件。
- 无边界循环和无法限制资源的执行。

### 7.5 工具状态

```text
draft → validating → preview → published → deprecated
             └→ validation_failed → draft
published → new draft → new published version
```

## 8. 工具生成闭环

### 8.1 流程

1. 识别会话中可复用的方法。
2. 判断一次性答案还是可重复工具。
3. 搜索现有工具。
4. 决定复用、升级或新建。
5. 明确用途、输入、输出和边界。
6. 转换成受支持执行步骤。
7. 补充来源、权限、异常处理和测试。
8. 提交 Novabox 校验。
9. 自动运行正常、边界和错误测试。
10. 右侧打开预览。
11. 用户确认后发布。

禁止“一句话直接发布”，必须走：

> 草稿 → 校验 → 测试 → 预览 → 用户确认 → 发布。

### 8.2 生成失败处理

以下情况不得假装生成成功：

- 规则缺失或相互矛盾。
- 来源无法确认却强依赖该来源。
- 输入输出无法结构化。
- 超出现有 DSL 和组件能力。
- 需要任意脚本或未授权系统能力。
- 测试失败且未修复。

系统应返回阻塞项、所需补充信息和建议扩展能力。

## 9. MCP 接口与 Agent 协作

### 9.1 稳定接口

不为每个工具注册一个顶层 MCP Tool，只暴露：

```text
novabox.search_tools
novabox.get_tool
novabox.run_tool
novabox.create_draft
novabox.validate_draft
novabox.publish_tool
novabox.list_tools
novabox.open_tool
```

这样工具数量增长时不会无限膨胀宿主工具列表。

### 9.2 新会话调用流程

```text
用户贴数据并明确 @Novabox
  → search_tools
  → 获取候选说明和输入 Schema
  → Agent 映射参数
  → run_tool 服务端再次校验
  → 执行
  → 返回结构化结果
  → 推送 UI 事件
  → 展开工具、填参、显示结果
```

### 9.3 自动执行策略

可默认自动执行：本地计算、格式转换、数据校验、只读查询。

必须二次确认：发送消息、修改远程数据、写入或删除文件、发布内容、支付、下单、调用有费用接口。

“@Novabox”是明确的用户指令约定，不依赖宿主是否提供特殊 @ 插件语法。

### 9.4 工具搜索

首版采用：

- 名称、关键词、标签匹配。
- 用途全文索引。
- 输入字段匹配。
- 最近使用与频率。
- Agent 对候选做最终语义判断。

返回候选、匹配分数、匹配原因、输入要求、权限和副作用。低置信时返回多个候选或未找到。后续再增加本地向量索引。

## 10. 提示词与 SOP

### 10.1 工具生成提示词

```text
你是 Novabox 工具构建器。

你的任务不是生成自由网页或任意脚本，而是生成符合
Novabox Schema 的可验证工具定义。

1. 先搜索现有工具，优先复用，不重复造工具。
2. 明确工具解决的问题、适用边界和不适用场景。
3. 将输入、处理步骤、输出分别结构化。
4. 只能使用受支持的组件、表达式和执行动作。
5. 不得生成 eval、任意系统命令或未声明的网络访问。
6. 不得编造业务规则、官方标准、来源或测试结果。
7. 外部规则必须给出来源；无法确认时标记待确认。
8. 信息不足时先提问，不得自行补全关键业务规则。
9. 必须提供正常、边界、错误输入测试用例。
10. 默认最小权限，不申请与工具无关的能力。
11. 生成结果只是草稿，不得绕过验证直接发布。
12. 修改已有工具时保留原版本并说明变更。
```

### 10.2 工具生成 SOP

```text
S1：识别本次会话中可复用的解决问题过程。
S2：判断这是一次性答案还是可重复工具。
S3：搜索现有工具，选择复用、升级或新建。
S4：定义用途、输入、输出和边界。
S5：把处理过程转换成受支持的执行步骤。
S6：补充来源、异常处理和权限声明。
S7：生成正常、边界和错误测试。
S8：提交 Novabox 校验并修复问题。
S9：在右侧预览并让用户确认。
S10：发布工具，返回名称、版本和后续调用方法。
```

### 10.3 新会话调用提示词

```text
当用户明确提到 Novabox 或 @Novabox 时：

1. 先调用 novabox.search_tools。
2. 根据用途和输入匹配现有工具。
3. 不得仅凭工具名称猜测功能。
4. 读取候选工具输入 Schema 和说明。
5. 将用户数据映射为结构化参数。
6. 缺少关键参数时先询问。
7. 参数校验失败时不得伪造执行结果。
8. 只读工具可以自动执行。
9. 有外部副作用的工具必须先获得用户确认。
10. 执行成功后返回结果，并通知桌面端展开页面。
11. 没有合适工具时明确说明，可建议创建草稿。
```

## 11. 数据、安全与维护

### 11.1 本地数据

- 工具包：独立文件，便于版本化和导出。
- SQLite：工具索引、设置、收藏、历史。
- 本地事件：使用 runId 保证 UI 与结果对应。
- 工具包不包含 API Key 等秘密信息。

### 11.2 安全

- 首版禁止任意生成代码直接运行。
- 表达式使用专用解释器。
- UI 不渲染未经处理的原始 HTML。
- 网络默认关闭，Host 白名单。
- 密钥放系统钥匙串，工具只保存引用名称。
- 运行超时、输入大小、列表长度限制。
- 副作用操作必须确认。

### 11.3 隐私

- 默认完全本地存储。
- 运行历史可关闭。
- 敏感输入可标记“不保存”。
- 日志默认不记录完整业务数据。
- 导出工具时排除密钥和历史。

### 11.4 版本与来源

- 草稿、已发布、已停用状态。
- 已发布版本不可变，支持回滚。
- 保存变更说明和来源摘要。
- 外部规则保存来源、访问日期和适用规则。
- 提供“来源可能过期”提示与重新核验入口。

## 12. 品牌、界面与交互摘要

详细规范见 `V1.0_ui_brand_design_20261028_V1.md`。

### 12.1 视觉方向

**Graphite & Mint / 石墨与薄荷**，定位为“精密工作仪器”，而不是营销型 AI 网站。

- 深色为默认，浅色完整支持。
- 暖灰背景降低纯黑疲劳。
- 薄荷绿只表示主操作、当前运行和成功连接。
- 琥珀色表示草稿、待确认和来源待复核。
- 不使用紫蓝渐变、玻璃拟态堆叠、漂浮光斑、机器人或魔法星图标。

### 12.2 界面原则

1. 窄窗口仍保持清晰主次，不把桌面后台硬压缩进来。
2. 工具任务优先于品牌装饰。
3. 输入、运行、结果形成稳定的纵向路径。
4. 不把所有内容做成同权重卡片。
5. 结果数字和状态具有清晰可扫读性。
6. 动画短促、可关闭，支持减少动态效果。
7. 所有操作具备 hover、focus、disabled、loading、empty、error、success 等状态。

### 12.3 关键交互

- Agent 开始搜索：右侧显示“正在查找工具”，不抢占宿主输入焦点。
- 找到工具：工具标题和匹配原因先出现。
- 自动填参：字段逐项更新并短暂标记来源，不让整页跳动。
- 运行完成：结果区更新，必要时轻提示，不强制滚动打断用户。
- 缺参：聚焦第一个缺失字段，同时 Agent 询问。
- 有副作用：结果区上方出现明确确认条。
- 草稿生成：显示校验和测试进度，失败可定位修复。
- 窗口解绑：保留独立使用能力，并提供重新贴靠入口。

## 14. 开发与验收顺序

### 阶段 0：窗口追随技术验证

- macOS/Windows 窗口识别。
- 移动、缩放、最小化、恢复。
- 最大化三种策略。
- 多显示器、DPI、宿主关闭。
- 验证通过后再绑定产品 UI。

- 工具包、Schema、执行 DSL。
- 工具库和通用工具页面。
- 本地运行、校验、测试、版本。

### 阶段 2：MCP 闭环

- Codex/CC 接入。
- 搜索、读取、运行。
- UI 自动打开、填参、显示结果。
- 新会话验证。

### 阶段 3：受约束生成

- 创建草稿、校验、测试、预览、发布。
- 生成提示词与 SOP。
- 来源、权限和失败处理。

### 阶段 4：视觉与发布加固

- 完整品牌 UI、深浅主题。
- 全状态、键盘、可访问性。
- 安全、性能、导入导出、诊断。
- 真实用户路径验收。

## 16. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 最大化时无外贴空间 | 提供工作区、覆盖、收起三种策略 |
| macOS 权限或事件差异 | 权限引导、事件+轮询、诊断工具 |
| 多宿主窗口识别错误 | 应用标识为主，允许手动绑定 |
| Agent 不主动调用 | 明确 @ 指令、Skill/SOP、清晰工具描述 |
| 工具生成质量不稳定 | 受约束 Schema、自动测试、预览确认 |
| 工具库增大后误匹配 | 元数据、置信度、候选确认，后续向量索引 |
| 规则过期 | 来源、日期、版本和复核提醒 |
| 任意代码安全风险 | V1.0 禁任意代码，最小权限 |
| UI 好看但难用 | 用户任务优先，窄窗与全状态真实验收 |
| 通用范围无限扩张 | 首版固定 DSL，超能力需求明确阻塞 |

## 17. V1.0 成功标准

产品是否成立，不以“生成了多少工具”为唯一指标，而看：

1. 用户是否能把一次会话沉淀成经过验证的工具。
2. 下次是否能脱离原会话重复使用。
3. Agent 是否能正确找到已有工具，而不是重新发明流程。
4. 手动与 Agent 调用是否得到一致结果。
5. 侧窗是否足够稳定、安静、好看，让用户愿意长期挂在工作区旁边。

最终形成的体验应是：

> **Codex/CC 继续负责理解与协作，Novabox 负责把方法留下来，并让它随时可用。**
